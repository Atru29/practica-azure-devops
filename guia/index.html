■ La arquitectura

  • Sale a internet
  • No sale de la red troncal de Azure
  • Dentro de la red virtual
Un grupo de recursos NO es una frontera de red El registro y la base de datos estan en el mismo grupo que la maquina, pero se dibujan fuera de la red virtual porque es donde estan de verdad: los dos tienen nombre publico. Un grupo de recursos es una carpeta de administracion y facturacion. Dos recursos no se hablan en privado por compartirlo: solo si comparten red virtual.
Que hace el service endpoint, que es lo interesante Azure SQL siempre tiene un nombre publico, database.windows.net. El service endpoint hace dos cosas: el trafico de la maquina a la base de datos no sale a internet, viaja por la red troncal de Azure; y el servidor solo acepta conexiones desde esa subred. Cualquiera que consiga la contrasena desde fuera no puede ni abrir la conexion. Y no cuesta nada.

El WAF de Azure usa OWASP CRS por dentro Cuando en el Proyecto01 se creo waf-proyecto01-prod con reglas OWASP, Azure estaba cargando el Core Rule Set. Es el mismo conjunto que puedes instalar gratis con ModSecurity en nginx. No pagas por las reglas, pagas por que se ejecuten antes de llegar a tu maquina.
Un WAF dentro y un WAF delante no son lo mismo Con Azure WAF el ataque nunca llega a tu servidor. Con ModSecurity, el ataque ya llego y lo bloquea tu propia maquina. Para inyeccion SQL o XSS da igual, se corta igual. Para un DDoS volumetrico no sirve: tu maquina ya se esta ahogando procesando el trafico. Eso solo lo resuelve algo por delante.

● La frontera real: las redes de Docker

Con una sola maquina, separar nginx y la API en dos subredes de Azure no protege nada: siguen siendo el mismo kernel y la misma tarjeta de red. La segmentacion que si existe aqui es la de Docker.

docker-compose.yml, la parte que importa 
services:
  nginx:
    ports:
      - "80:80"
      - "443:443"        # el UNICO que publica puertos
    networks: [frontal, interna]

  angular:
    networks: [frontal]      # sin ports: no escucha en el anfitrion

  api:
    networks: [interna]      # solo nginx la alcanza
Por que esto es segmentacion de verdad La API no es alcanzable desde internet aunque abrieras el 8080 en el NSG, porque no esta publicada en el anfitrion. Solo existe dentro de la red interna de Docker, y el unico contenedor que esta en ella es nginx. Cuesta cero y es lo que hace cualquier despliegue serio de un solo servidor.
Cuando si harian falta dos subredes Cuando haya dos maquinas: nginx en snet-web con IP publica, y la API en snet-app sin ella, con un NSG que solo permita el 8080 entre ambas. Eso cuesta una segunda VM, unos 7,60 USD al mes, porque las 750 horas gratuitas cubren una sola.

02 Red virtual y subred

Una sola subred, la de la maquina. Azure SQL no se inyecta en la red como haria PostgreSQL: se le concede acceso desde esta subred mediante un service endpoint.

la red y la subred de la maquina 
az network vnet create \
  --resource-group rg-demo01-prod \
  --name vnet-demo01-prod \
  --location centralus \

Cuanto mayor el numero, mas pequeno el trozo. Es al reves de lo que parece.

Azure se reserva 5 direcciones en cada subred En 10.50.1.0/24: la .0 identifica la red, la .1 es la puerta de enlace, la .2 y la .3 son el DNS de Azure y la .255 es la difusion. Quedan 251 utilizables y la primera que reparte es la .4.
Por eso la maquina sera 10.50.1.4, y por eso en el Proyecto01 eran 10.20.0.4 y 10.30.0.4. No fue casualidad.
Si calculas una subred al milimetro, resta siempre 5: un /29 tiene 8 direcciones y solo te deja 3.
Por que dividir en subredes si solo hay una maquina Porque la subred es donde se enganchan cosas que a nivel de red no existen solas: el NSG se asocia a una subred, el service endpoint se activa por subred, y las delegaciones son por subred.
Por que 10.50 y no 10.0 El Proyecto01 uso 10.20 para qa y 10.30 para prod. Dos redes con el mismo rango no se pueden emparejar nunca, asi que conviene no repetir aunque hoy esten solas.
Los comandos create de Azure son idempotentes Ejecutar el mismo create dos veces con los mismos parametros no duplica nada ni da error: Azure compara lo declarado con lo existente y se queda igual. Es el mismo principio del que vive Bicep, solo que aqui depende de que repitas exactamente los mismos valores.

☰ La arquitectura del backend

Una Web API que devuelve JSON — no MVC con vistas: la pantalla la pinta Angular en el navegador. Un solo proyecto, organizado en modulos, con todo el acceso a datos por procedimientos almacenados.

Que hace cada capa, y que NO hace

Servicio las reglas: quien puede hacer que, en que orden, con que estado saber que existe HTTP ni que existe Dapper

CREATE OR ALTER PROCEDURE dbo.usp_Matricula_Solicitar
    @i_alumnoId   INT,
    @i_periodoId  INT,
    @v_cursos     VARCHAR(500)      -- '1,3,7'
AS
BEGIN
    SET NOCOUNT ON;
    SET XACT_ABORT ON;

    ---------------------------------------------------------- validaciones
    IF NOT EXISTS (SELECT 1 FROM dbo.Alumno WHERE Id = @i_alumnoId AND Activo = 1)
        THROW 50020, 'El alumno no existe o esta inactivo.', 1;

    IF NOT EXISTS (SELECT 1 FROM dbo.PeriodoAcademico
                   WHERE Id = @i_periodoId AND Estado = 'Abierto')
        THROW 50001, 'El periodo no existe o no esta abierto.', 1;

    IF EXISTS (SELECT 1 FROM dbo.Matricula
               WHERE AlumnoId = @i_alumnoId AND PeriodoId = @i_periodoId)
        THROW 50010, 'El alumno ya tiene una matricula en este periodo.', 1;

    DECLARE @Cursos TABLE (CursoId INT PRIMARY KEY);

    INSERT INTO @Cursos (CursoId)
    SELECT DISTINCT TRY_CAST(value AS INT)
    FROM   STRING_SPLIT(@v_cursos, ',')
    WHERE  TRY_CAST(value AS INT) IS NOT NULL;

    DECLARE @creditos INT =
        (SELECT SUM(cu.Creditos) FROM @Cursos c JOIN dbo.Curso cu ON cu.Id = c.CursoId);

    IF @creditos > 24
        THROW 50004, 'La matricula supera el maximo de 24 creditos.', 1;

    ---------------------------------------------------------- escritura
    BEGIN TRANSACTION;

        INSERT INTO dbo.Matricula (AlumnoId, PeriodoId)
        VALUES (@i_alumnoId, @i_periodoId);

        DECLARE @id INT = SCOPE_IDENTITY();

        INSERT INTO dbo.MatriculaCurso (MatriculaId, CursoId)
        SELECT @id, CursoId FROM @Cursos;

    COMMIT TRANSACTION;

    SELECT MatriculaId = @id, Estado = 'Solicitada', Creditos = @creditos;
END

Cuatro detalles que separan un procedimiento correcto de uno fragil

1 — SET XACT_ABORT ON Sin esto, un error a mitad de la transaccion la deja abierta y las escrituras anteriores aplicadas. Con el, cualquier error deshace todo automaticamente. Es una linea y evita datos a medias.
2 — WITH (UPDLOCK, HOLDLOCK) al leer antes de decidir En usp_Matricula_Aprobar se lee el estado y despues se actualiza. Entre esas dos operaciones, otro gestor podria aprobarla tambien: los dos leerian "Solicitada" y los dos escribirian. El bloqueo mantiene la fila reservada hasta el final de la transaccion.
leer y decidir sin que nadie se cuele 
SELECT @estado = Estado
FROM   dbo.Matricula WITH (UPDLOCK, HOLDLOCK)
WHERE  Id = @i_matriculaId;

IF @estado <> 'Solicitada'
    THROW 50011, 'Solo se puede aprobar una matricula en estado Solicitada.', 1;
3 — SCOPE_IDENTITY(), nunca @@IDENTITY Los dos devuelven el ultimo id generado, pero @@IDENTITY devuelve el de cualquier insercion, incluida la que haga un disparador en otra tabla. Si manana alguien anade un disparador de auditoria, @@IDENTITY empieza a devolver el id equivocado y el fallo es dificilisimo de encontrar. SCOPE_IDENTITY() se limita a tu propio ambito.
4 — validar primero, escribir despues Todas las comprobaciones van antes de BEGIN TRANSACTION. Asi la transaccion dura lo minimo y bloquea lo minimo. Lo que no se puede sacar fuera — como leer el estado para decidir— va dentro y con bloqueo.

Registro de errores en la base

Los 14 procedimientos que escriben llevan TRY...CATCH y dejan rastro en dbo.ErrorLog.

La trampa: el log tambien se deshace Si registras el error dentro de la transaccion, el ROLLBACK borra la fila del log justo cuando mas falta hace. El orden dentro del CATCH es siempre:
1. ROLLBACK — deshacer lo que quedo a medias
2. registrar — ya fuera de la transaccion, asi persiste
3. THROW — relanzar el error original
el bloque CATCH, identico en los 14 
BEGIN CATCH
    IF XACT_STATE() <> 0 ROLLBACK TRANSACTION;

    DECLARE @v_log NVARCHAR(1000) =
        CONCAT('@i_matriculaId=', @i_matriculaId, ' @i_gestorId=', @i_gestorId);
    EXEC dbo.usp_Error_Registrar @v_parametros = @v_log;

    THROW;
END CATCH
DetallePor que
XACT_STATE() <> 0 antes del ROLLBACK si no hay transaccion activa, el ROLLBACK falla y tapa el error original
THROW sin argumentos relanza el error tal cual; con argumentos inventarias uno nuevo y perderias el numero
El CONCAT de parametros sin ellos sabes que fallo, pero no con que datos. Reproducirlo seria adivinar
La contrasena nunca se registra usp_Alumno_Crear recibe @v_clave y la omite del log a proposito

Separar reglas de negocio de fallos reales

Tres tropiezos de T-SQL que costaron tiempo

1 — EXEC no acepta expresiones como parametro

DECLARE @v_log NVARCHAR(1000) = CONCAT(...);                -- BIEN
EXEC dbo.usp_Error_Registrar @v_parametros = @v_log;
En EXEC proc @param = X, la X solo puede ser una constante o una variable. Nunca una llamada a funcion.
2 — sqlcmd trae QUOTED_IDENTIFIER desactivado Crear la tabla fallaba con Msg 1934: una columna calculada PERSISTED exige QUOTED_IDENTIFIER ON, y sqlcmd lo trae OFF por defecto. Se arregla poniendo los SET al principio del fichero, o lanzando sqlcmd -I.
3 — los parametros truncan en silencio Pasar 200 caracteres a un parametro NVARCHAR(120) no da error: recorta a 120 y sigue. Solo al insertar en una columna mas corta salta "String or binary data would be truncated". Conviene validar la longitud en el API, porque la base no va a avisar.
Las lecturas no llevan TRY...CATCH Decision consciente: no hay nada que deshacer y un error de lectura sube igual al cliente. Anadirlo seria ruido en 11 procedimientos a cambio de nada.

12 El registro de imagenes

La maquina no construye nada: docker-compose.prod.yml descarga las imagenes ya hechas. Hace falta un sitio de donde descargarlas, y ese es Azure Container Registry (ACR). Las imagenes se construyen en el portatil (o en el pipeline), se suben al registro y la maquina solo hace pull.

Tres nombres para lo mismo Antes de crearlo, el repositorio tenia el registro con tres nombres distintos: acrdemo01prod en esta guia, acrmatriculas en .env.prod.ejemplo y acrdemo01 en .env.prod. Ninguno existia en Azure. Se unifico en acrdemo01prod, que sigue la convencion de nombres del paso 01.

Dar permiso a la maquina

La maquina se creo con identidad administrada: Azure le dio una identidad propia en Entra ID, como si fuera un usuario. Ahora hay que darle a esa identidad permiso para leer el registro. Eso es RBAC: un rol asignado a una identidad sobre un ambito.

Tres cosas que hay que saber de un JWT

1. Firmado no es cifrado Cualquiera puede leer los datos: esta misma seccion lo hace con el de Ana. Nunca se mete un secreto en un JWT. Lo que garantiza la firma es que nadie lo ha modificado: cambiar alumnoId invalida la firma y la API da 401.
2. No se puede revocar uno solo La API no guarda los tokens, solo comprueba firma y fecha. Un token robado vale hasta su exp aunque Ana cierre sesion. Por eso importan la duracion corta, ClockSkew = 0 y HTTPS. Para invalidarlos todos de golpe: cambiar JWT_CLAVE.
3. localStorage lo lee JavaScript Si la aplicacion tuviera un fallo XSS, el codigo inyectado podria leer el token. La alternativa es una cookie HttpOnly, que JavaScript no ve, a cambio de tener que protegerse de CSRF. Las cabeceras de web/seguridad.inc son parte de la defensa.

19 HTTPS con Let's Encrypt

Hasta aqui todo iba por http://: la contrasena del login, el JWT y los PDF viajaban en claro entre el navegador y la maquina. Las reglas de acceso de la seccion 15 no sirven de nada si alguien en la misma red copia el token. Ahora el nginx del contenedor web termina el TLS, con un certificado gratuito de Let's Encrypt que se renueva solo.

el diseno 
Internet ─► NSG (80, 443) ─► maquina
                              ├ :80  ─► web :8080  → 301 a https  (salvo /.well-known/acme-challenge/)
                              └ :443 ─► web :8443  → TLS + Angular + /api ─► api:8080
                                            ▲
                    /etc/matriculas-tls ────┘  certificado (copia con dueno uid 101, solo lectura)
                    /var/www/certbot   ─────┘  retos de renovacion (solo lectura)
   certbot en la maquina: emite y renueva; el deploy hook copia y recarga nginx
DecisionPor que
TLS en el nginx que ya habiaYa era el proxy inverso. Es lo que preveia "Por que sin gateway"
Contenedor en 8443, publicado como 443nginx corre sin privilegios: no puede abrir puertos por debajo de 1024. Igual que 80 → 8080
El 80 solo redirigeSalvo la ruta del reto: Let's Encrypt comprueba que el dominio es tuyo pidiendo un fichero por HTTP (metodo HTTP-01)
Un deploy hook copia el certificadocertbot deja la clave legible solo por root, y nginx en el contenedor es el uid 101
HSTS de 1 diaSi el certificado fallara, un max-age de un ano dejaria a los usuarios fuera durante meses. Se sube cuando lleve tiempo estable
TLS 1.2 y 1.31.0 y 1.1 estan rotos y ningun navegador actual los necesita

21 Observabilidad: Prometheus y Grafana

Hasta aqui la aplicacion funciona, pero si algo fallara a las 3 de la manana nadie se enteraria hasta que un alumno se quejara. Observabilidad es poder responder "que esta pasando dentro" sin entrar a la maquina.

PilarQue esPregunta
MetricasNumeros a lo largo del tiempoCuanto, y si va a peor
LogsEventos con texto y horaQue paso exactamente
TrazasEl recorrido de una peticion por todas las piezasDonde se pierde el tiempo

La pila, y por que esa

Lo mas extendido en DevOps es software libre de la CNCF y de Grafana Labs: OpenTelemetry para instrumentar, Prometheus para metricas, Loki para logs, Tempo para trazas y Grafana para verlo todo. Se monta por fases; la primera, solo metricas de la maquina.

PiezaVersionQue hace
node_exporterv1.12.1Lee CPU, RAM, disco y red del anfitrion y los publica en /metrics
Prometheusv3.15.0Proyecto graduado de la CNCF. Recoge y guarda series temporales; se consulta con PromQL
Grafana13.2.4Solo dibuja: no guarda datos, necesita una fuente (aqui, Prometheus)
Por que no solo Grafana, ni Azure Monitor Grafana sin fuente de datos muestra "No data": es la pantalla, no la senal. La alternativa de una sola pieza era Grafana leyendo Azure Monitor con la identidad de la maquina, pero Azure no ve la RAM ni el espacio libre sin instalar un agente, y se aprende menos de lo que se usa fuera de Azure. El coste de esta pila es 0: no crea recursos, cabe en la RAM y el disco que ya se pagan, y no abre puertos.
Su punto debil: vive en la maquina que vigila Si la maquina se cae o se llena el disco, Prometheus cae con ella y nadie avisa. En produccion real la observabilidad va fuera de lo que vigila; aqui se compensara con una prueba de disponibilidad externa de Azure (fase de alertas).

Como sabe Grafana los datos de la maquina

Grafana no sabe nada de la maquina. El dato pasa por cuatro manos:

QuienQue hace
1. El kernelLleva la cuenta de todo y lo expone en ficheros virtuales: /proc/meminfo, /proc/stat, /sys/.... No estan en disco: se generan al leerlos. free, top y df leen lo mismo

El codigo

Program.cs (lo esencial) 
var destinoOtel = builder.Configuration["Otel:Endpoint"];
if (!string.IsNullOrWhiteSpace(destinoOtel))        // en local, sin destino, no cambia nada
{
    builder.Services.AddOpenTelemetry()
        .ConfigureResource(r => r.AddService("matriculas-api", serviceVersion: version))

            .AddAspNetCoreInstrumentation()
            .AddHttpClientInstrumentation()
            .AddSqlClientInstrumentation()
            .AddRuntimeInstrumentation()

                exportador.Endpoint = new Uri(destinoOtel);
                lector.PeriodicExportingMetricReaderOptions.ExportIntervalMilliseconds = 15_000;

}

▲ Llevarlo a produccion real: arquitectura y coste

Lo construido es un laboratorio: una sola maquina con todo dentro, ideal para aprender porque cada pieza se ve y se toca. Una empresa no lo pondria asi en produccion: si la maquina cae, cae todo; los parches, el disco y los certificados son trabajo propio; y la observabilidad vive dentro de lo que vigila. La pregunta de arquitectura es que servicio gestionado de Azure sustituye a cada pieza, y cuanto cuesta.
